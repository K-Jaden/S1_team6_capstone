# AI 생성 작품 품질 검증 프레임워크 (팀 논의용 초안)

> 이 문서는 아직 확정된 사양이 아니라, 팀 논의를 위한 제안입니다. 합의된 뒤 실제 파이프라인(critique 그래프)에 게이트로 구현할 예정입니다.

> **설계 제약 (중요): 무료 API 티어.** Gemini(flash-lite/1.5-flash), Cloudflare Workers AI 모두 대부분 무료 티어로 운영 중이다. 이 문서의 모든 결정은 "토큰/호출 횟수를 최대한 아낀다"는 전제를 깔고 판단하며, 추가 API 호출이 필요한 방법은 특히 신중히 채택한다.

## 배경 및 문제의식

ArtPlanningDAO의 핵심 기능 중 하나는 "커뮤니티의 방향성을 담은 그림을 생성하는 것"이다. 그런데 여기서 애매함이 하나 생긴다:

> 커뮤니티가 원해서 어린이 일기장에 나올 법한 순박한 화풍의 그림이 나왔다고 하자. 미술적 완성도만 놓고 보면 "저품질"에 가까워 보이는데, 이걸 검증 절차에서 걸러야 하는가?

이 질문에 "예/아니오"로 바로 답하려고 하면 기준이 안 잡힌다. 이유는 **"완성도"와 "커뮤니티 취향"이 서로 다른 두 개의 축인데, 이걸 하나의 점수로 뭉뚱그려 판단하려고 하기 때문**이다. 이 문서는 두 축을 분리해서 각각 다른 방식으로 검증하는 프레임워크를 제안한다.

## 핵심 원칙: 두 축을 분리한다

| | 축 A — 실행 품질 (완성도) | 축 B — 커뮤니티 적합성 |
|---|---|---|
| 질문 | 의도한 것을 제대로 구현했는가? | 이 커뮤니티가 원하는 방향과 맞는가? |
| 판단 대상 | 화풍의 "수준"이 아니라 "그 화풍답게 잘 만들어졌는가" | 투표 결과·방향성 요약본과의 일치 여부 |
| 판단 주체 | AI(critic 에이전트 / 정량 지표) | 커뮤니티 (VP 투표) |
| 예시 | 어린이 낙서 화풍을 요청 → 낙서답게 자연스럽게 나왔으면 통과 | 어린이 낙서 화풍이 실제로 유저 투표로 선택됐으면 그 자체로 적합 |
| 걸러야 하는 경우 | 신체 왜곡, 텍스트 깨짐, 프롬프트 요소 누락 등 **의도치 않은 실패** | (AI가 판단하지 않음 — 아래 참고) |

**가장 중요한 결정: 축 B는 AI가 판단하지 않는다.** "무엇이 좋은 예술인가"는 이 프로젝트의 정체성(DAO 거버넌스 — 커뮤니티가 방향을 정한다)상 원래 투표가 심판하는 영역이다. AI 검증 시스템이 여기 개입해서 "저품질이라 탈락"시키면 DAO 철학과 정면충돌한다. 따라서:

- **AI는 축 A(망가지지 않았는가)만 게이트로 건다.**
- **축 B(좋은 예술인가/커뮤니티에 맞는가)는 100% VP 투표에 위임한다.**

## 축 A 검증 방법론: 체크리스트 기반 평가 (Rubric)

"이 그림 괜찮아?" 같은 통짜 질문은 판단자(사람이든 LLM이든)마다 기준이 갈린다. 대신 관찰 가능한 예/아니오 항목으로 쪼갠다.

### 검토한 대안과 채택 이유

AI 생성 이미지 검증에 쓰이는 알고리즘을 4개 카테고리로 조사하고 비교했다.

| 카테고리 | 대표 알고리즘 | 채택 여부 | 이유 |
|---|---|---|---|
| **VQA & 논리 분해** | TIFA, DSG, VQAScore | ✅ **채택** | 프롬프트를 원자적 요소(주체/화풍/재질)로 쪼개 Yes/No로 검증하는 방식 — 이미 쓰고 있는 Gemini가 멀티모달이라 이미지를 그대로 입력해 검증 가능. **새 인프라·모델 없이 기존 LLM 호출 방식 그대로 확장**된다. 위 체크리스트가 사실상 이 방법론을 구현한 것 |
| 임베딩 기반 전역 유사도 | CLIPScore, ECO, NegCLIP | 🔸 보류(선택) | 별도 CLIP 모델을 새로 붙여야 하고, 전역 유사도 하나의 스칼라값이라 "무엇이 구체적으로 잘못됐는지" 체크리스트 형태로 안 나옴. 재수정 루프에 필요한 "실패 사유"를 못 줌. 가벼운 보조 수치로만 여지를 남김 |
| 인간 선호도 보상 모델 | PickScore, ImageReward, HPSv3 | ❌ **기각** | 이 모델들은 "인간이 실제로 미적으로 선호하는가"를 학습한 리워드 모델이라 결과적으로 "예쁘고 사실적인 이미지"에 편향된다. **축 B(취향)는 AI가 판단하지 않는다는 원칙과 정면으로 충돌** — 커뮤니티가 일부러 고른 순박한 화풍을 "미적 결함"으로 감점시킬 위험이 있어 축 A에 쓰기엔 부적합 |
| 객체 탐지 & 기하학적 제약 | UniDet, MiDaS, PCMDE | ❌ **기각** | "A가 B 왼쪽에 있다" 같은 정밀 공간관계 검증용인데, 우리 프롬프트는 "[테마들], in the style of [화풍]" 구조라 복잡한 다중 객체 공간관계를 요구하지 않음. 객체 탐지기·깊이 추정 모델을 로컬에 띄우려면 GPU 인프라가 필요해 지금 규모(API 호출 위주 아키텍처)에 과함 |

### 제안 체크리스트 (TIFA/DSG 방식 — Gemini 멀티모달로 구현)

critic 노드가 프롬프트를 원자적 요소로 분해한 뒤, 생성된 이미지를 Gemini에 함께 입력해 각 항목을 Yes/No로 검증한다 (구조화 출력 스키마로 받음):

- [ ] 프롬프트에 명시된 핵심 요소(주제·화풍·재질)가 실제로 이미지에 나타나는가? — 요소별로 각각 Yes/No
- [ ] 구조적 결함이 있는가? (신체 왜곡, 텍스트 깨짐, 심각한 아티팩트, 좌우 비대칭 오류 등)
- [ ] 해당 화풍의 관습을 따르고 있는가? ("고급스러운가"가 아니라 "그 화풍답게 나왔는가")
- [ ] title/description/image_prompt가 서로 내용상 일치하는가? (설명은 로봇인데 프롬프트는 동물을 그리는 식의 불일치 방지)

각 항목은 통과/실패 이진 판정만 하고, "몇 점짜리 작품인가" 같은 스칼라 점수는 매기지 않는다. 하나라도 실패하면 재수정 대상이며, 실패한 구체적 항목을 painter에게 그대로 전달해 재수정 프롬프트에 반영한다.

### 정량 지표 보조 (선택, 우선순위 낮음)

- CLIP score 등으로 "생성된 이미지가 실제로 프롬프트와 관련 있는가"를 수치화하는 방안도 있으나, 별도 인프라가 필요하고 TIFA/DSG 체크리스트만으로 충분히 커버되므로 우선순위는 낮게 둔다.

## 프로세스 구조 (3단계)

1. **자동 게이트 (Gemini 멀티모달 기반 VQA 체크리스트, 축 A만)** — critic 에이전트가 이미지+분해된 질문을 Gemini에 함께 입력해 이진 판정. 실패 시 painter에게 구체적 실패 항목과 함께 재수정 요청 (비평-수정 루프).
2. **정량 지표 보조 (선택)** — 필요시 CLIP score 등으로 축 A 판정을 보강. 우선순위 낮음, 1단계만으로 시작.
3. **최종 심판은 커뮤니티** — 축 B는 지금과 동일하게 VP 투표가 전담. AI는 이 단계에 관여하지 않음.

## 축 A 게이트의 실행 시점과 이미지 전달 방식

**현재 구조의 빈틈**: 이미지 실제 생성(Cloudflare FLUX 호출)은 `backend`(`main.py`의 phase2-generate)가 담당하고, `ai_core`의 candidates 그래프는 title/description/image_prompt **텍스트만** 생성한다. critic도 지금은 텍스트만 보고 비평문을 쓰며, **생성된 이미지 자체를 본 적이 없다.** 따라서 이 게이트를 넣으려면 "critic이 실제 이미지를 언제·어떻게 전달받는가"부터 정해야 한다.

> ⚠️ 아래 내용은 이후 "토큰 절약형 전략" 논의에서 **검증 범위를 우승작 1개(phase3, 투표 종료 후)로 좁히기로 결정**하면서 시점이 갱신됨. phase2 시점엔 이미지를 5개 다 만들지만 검증은 하지 않고, phase3에서 우승작 1개만 검증한다.

**이미지 전달 방식 — 검토한 두 옵션 (base64 vs URL)**

1. ✅ **채택 — base64 inline data**: Gemini API는 임의의 외부 URL을 직접 fetch하지 못하고 base64 inline data만 받으므로, 결국 어느 시점에 하든 바이트를 base64로 인코딩해서 넘겨야 한다. phase3 시점엔 phase2에서 이미 `static/images/roundN_cX.png`로 저장이 끝난 뒤이므로, backend가 **해당 파일을 디스크에서 읽어 base64로 인코딩**한 뒤 ai_core에 전달한다 (Cloudflare 응답 시점의 메모리상 base64는 phase2와 phase3 사이에 투표 기간이 끼어 있어 이미 사라진 뒤라 재사용 불가).
2. ❌ 기각 — ai_core가 static URL로 직접 재조회: 어차피 Gemini에 넘기려면 base64가 필요하므로 "URL만 전달"은 성립하지 않고, ai_core가 별도로 HTTP GET을 해야 하는 불필요한 왕복만 늘어난다. backend가 이미 파일에 접근 가능하니 backend에서 바로 읽어 인코딩하는 게 가장 짧은 경로.

**결론적 흐름**: 유저 투표 종료 → `phase3-valuation`에서 우승작 확정 → backend가 우승작의 저장된 이미지 파일을 읽어 base64로 인코딩 → 새 엔드포인트 `POST /api/agent/quality-check`(가칭)로 base64 이미지 + image_prompt/title/description을 ai_core에 전달 → critic이 TIFA/DSG 체크리스트로 Yes/No 판정 → 실패 시(최대 1회) backend가 우승작만 Cloudflare 재호출(재수정), 최종 실패해도 안전 렌더링 폴백으로 진행.

## 재시도가 품질을 보장하지 않는 이유와 토큰 절약형 전략

단순히 "실패하면 다시 만든다"는 재시도 자체는 품질을 보장하지 않는다 — 같은 프롬프트로 다시 생성하면 그냥 또 다른 무작위 뽑기일 뿐이다. 재시도가 실제로 효과 있으려면 **"왜 실패했는지"가 다음 시도에 구체적으로 반영**돼야 한다. 아래 방법들을 무료 티어 제약 하에서 "추가 API 호출이 드느냐"를 기준으로 정리한다.

| 방법 | 추가 API 호출 비용 | 채택 여부 |
|---|---|---|
| **구체적 실패 사유 재주입** (막연히 "실패"가 아니라 "로봇이 없음" 식으로 정확히 전달) | 없음 — 어차피 하는 재시도 호출에 프롬프트 텍스트만 추가 | ✅ **채택 (필수 기반)** |
| **실패 유형별 분기 대응 + 프롬프트 내 회피 문구** (구조적 결함 방지 문구를 프롬프트에 녹임, 요소 누락엔 프롬프트 재작성) | 없음 — 같은 Cloudflare 호출에 텍스트만 추가 | ✅ **채택 — 최우선** (재시도 자체가 덜 필요해짐) |
| 병렬 Best-of-N (변형 여러 개 동시 생성 후 최선 채택) | 있음 — 호출 수가 N배로 증가 | ❌ **기각** — 무료 티어 소진 위험이 큼 |
| 탈출 조건(N회 실패 시 폴백) | 없음 — 기존 "안전 렌더링" 폴백 패턴 재사용 | ✅ **채택** |

**핵심 전략 전환: "사후 재시도"보다 "사전 예방"에 투자한다.** 프롬프트에 회피 문구를 녹이거나 구조화된 프롬프트를 쓰는 것처럼 **추가 호출이 전혀 없는 방법**으로 첫 시도의 성공률 자체를 높이면, 애초에 재시도가 필요한 횟수가 줄어든다. 이게 토큰 절약과 품질 향상을 동시에 만족시키는 유일한 방향이다.

> **확인 완료 — Cloudflare `flux-1-schnell`은 `negative_prompt`를 지원하지 않는다.** 공식 문서(developers.cloudflare.com/workers-ai/models/flux-1-schnell) 기준 입력 파라미터는 `prompt`(필수)와 `steps`(선택, 기본 4·최대 8)뿐이다. `schnell` 계열은 애초에 classifier-free guidance 없이 증류된 초고속 모델이라 negative_prompt 자체가 구조적으로 의미가 없는 부류이기도 하다. 따라서 **우회 방법을 그대로 채택**한다: "avoid: 신체 왜곡, 여분의 팔다리, 텍스트 깨짐" 같은 회피 문구를 별도 파라미터가 아니라 `prompt` 문자열 자체에 이어붙인다. 부수적으로 `steps`를 기본값 4에서 최대치 8로 올리는 것도 추가 호출 없이 품질을 높이는 무료 레버다 (단, 생성 시간은 늘어남 — 이미 이미지당 6초 대기가 있으니 체감 영향은 적을 것으로 예상).

### 재시도 횟수와 검증 범위 결론

- **재시도는 최대 1회로 제한한다.** 1회 재수정 후에도 실패하면 기존 "안전 렌더링" 폴백으로 넘어간다 — 무한정 API를 소모하며 매달리지 않는다.
- **VQA 게이트는 5개 후보 전부가 아니라 "우승작 1개"에만 전체 적용한다.** 5개 후보 모두에 이미지 검증을 걸면 라운드당 Gemini 비전 호출이 5배가 되는데, 실제로 온체인에 영구 기록되고 경매되는 건 우승작 하나뿐이다. 5개 후보 생성 단계에서는 비용이 0인 예방책(프롬프트 내 회피 문구, steps 상향)만 적용하고, 전체 체크리스트 검증은 투표가 끝나고 우승작이 정해진 뒤 critique 단계에서 1회만 수행한다.
  - **트레이드오프 인지**: 이렇게 하면 투표 단계에서 유저가 보는 5개 후보 중 일부는 검증을 안 거친 채로 노출될 수 있다. 무료 티어 제약상 받아들이는 한계이며, 예방책(프롬프트 내 회피 문구)만으로 이 단계의 결함 발생률 자체를 낮추는 데 기댄다.

## 이 프로젝트 철학과의 정합성

DAO의 존재 이유는 "탈중앙화된 커뮤니티가 방향을 정한다"는 것이다. 만약 검증 시스템이 축 B(취향)까지 AI가 판단해서 필터링해버리면, 사실상 AI가 큐레이터 권력을 갖게 되어 DAO의 거버넌스 철학과 모순된다. 이 프레임워크는 **"AI는 완성도만 보증하고, 무엇이 좋은 예술인가는 끝까지 커뮤니티가 결정한다"**는 원칙을 지킴으로써 이 모순을 피한다.
